## Reports（2026-10-09 读取 HID descriptor）

- Input `0x01`：63 bytes；布局为 `[1]` channel tag，`[2:4]` little-endian 长度，`[4:]` payload（event id、长度、值）。
- Output `0x02`：M0 为 63 bytes，按键为 **319 bytes**。
- Feature `0x03`（set），及 M0 的 `0x2D..0x36` / 按键的 `0x37..0x3E`：各 31 bytes。

**滚轮 SET_IDLE 细节**：固件 01.00.03.01 在主机发送 HID class request SET_IDLE（`21 0A 0000 0000 0000`，duration 0，interface 0）前完全不发送 input report。Windows HID driver 对每个 HID 设备都会发送，macOS 不发，因此 Mac 滚轮无声，重新装回无效，GET_IDLE 前后均为 0。用 `prototype/tools/hid_idle.py --set` 发送后，两个滚轮立即生效（主人设备，2026-10-15 16:56）。HubDeck 现在在 macOS 连接每个 M0 模块时发送。旋钮固件 01.00.05.00 无需此操作便会报告；滚轮 HID descriptor 与旋钮相同（Consumer page `0x0C`、63 B input report 1、output 2、features 3、2D–31、36）。2026-10-15 没有听到 session 9 的啸叫。

2026-10-09 用坐标网格与照片测量，按键 `i` 显示从 `((i % 5) * 102, (i / 5) * 100)` 开始的 72×72 方块；即 x=0、102、204、306、408，y=0、100、200。按键到达面板边缘，水平 30 px、垂直 28 px 间隙被外框遮住。

更精确的双框校准（主人，2026-10-09）为：可视窗口 **79×75 px**，列间距 100、行间距 99、起点 (0,0)，应用默认如此。窗口并非完全均匀，难以 15 键全部逐像素对齐。此 Windows 设备的 15 张单键图共 18 KB、18 ms；整面板 13.6 KB、11 ms。USB 不是瓶颈；应用把按键画在整面板图中，以同时变化。

## 图片帧率（2026-10-10 测量）

参考设备执行 `cargo run --release -p mh-device --example framerate -- 4 <quality>`：480×272 整面板与 240×240 dial 图片均约 **32 fps**。JPEG quality 80（面板约 7 KB、dial 约 4 KB）和 60（约 5 KB、3 KB）相同，两个模块同时发送也各约 32 fps。限制在设备侧，不在图片大小；尚未目视确认屏幕是否显示了每一帧。

`jpeg-encoder` crate 生成的 baseline JPEG（默认 chroma sampling、quality 80–98）与 `image` crate 一样可供按键面板和 dial 使用：2026-10-15 在 PC 上以 release gate 最繁忙配置和 film 配置核对，窗口 dial 镜像显示的就是设备收到的字节。

## 底座朝向与模块位置（2026-10-09）

- **朝向**：底座有传感器，转动时 report `0x35` 和 event `0x2B` 在 `01`、`00` 间切换。官方应用把 1 视为 horizontal，其余为 vertical，只区分两种状态。参考设备平放为 `01`，竖立为 `00`。2026-10-09 20:25–20:28，每次右转 90° 的四位置测试：初始 `01`、90° `00`、180° `01`、270° `01`。这是单向倾斜开关，不是 accelerometer；只把右转 90°（支架上直立）与其余位置区分。应用自动横竖加四方向手动旋转，按底座保存。早期所谓每 0.5 s heartbeat 实为相同朝向报告。直立 `00` 的绘制旋转为 180（主人设备，2026-10-14；0 时全倒，平放仍为 270）。开关可能卡住：2026-10-13 搬到 Mac 后，平放仍读 vertical，稍抬才恢复，属机械而非软件问题；可用手动旋转覆盖。
- **位置与旋转**：底座含 Prolific `067B:2586` USB hub 树。模块相对最上级底座 hub 的端口路径（如 `1-4-3`）标识 slot，继而确定位置和角度。官方应用以 CSS 的 `pos` + path 映射，两朝向共 99 条规则。Windows 从 `DEVPKEY_Device_LocationPaths` 读取，如 `…#USB(6)#USB(1)#USB(4)#USB(3)`；macOS 用 `locationID`。参考设备 2026-10-09：dial `1-3-4`、knobs `1-4-3`、keys `2-3`、rollers `3-3`、base MCU `1-4-4`。

### 插槽表（2026-10-09）

`prototype/tools/gen_slots.py` 将官方布局的 88 个“模块 + slot”组合换成我们的 4×6 网格单元和旋转。官方板相对本项目转了 180°，旋钮与滚轮图又差 180°。在参考设备 identify mode（按键数字、dial 箭头、LED 颜色、滚轮预览）核实 keys@2-3、dial@1-3-4、knobs@1-4-3、rollers@3-3、faders@1-1-3，其中推杆按表放置无需修正。旋钮顺序为 2 在左、1 在右、3 在下。应用优先级：用户手动布局 > 表 > 推测。

**任意模块可接任意连接器（2026-10-19）**：主人确认全部 26 个连接器可用；官方表遗漏了 42 种超出底座边缘的组合，例如 keys `1-1-1`（issue #4 用户：keys、faders `2-3`、knobs `1-3-4`、dial `1-4-1`，24 格底座容纳 28 格模块），或 keys `4-4`（主人 2026-10-19 12:21）。

拟合模型把每个连接器视为底座上的一个有方向的点，每类模块有自己的底部连接点（未旋转 footprint：dial (1,0)、keys (3,1)、faders (3,0)、knobs (1,2) 转 180、rollers (2,0) 转 270），匹配已知 62 对中的 58 对。不匹配的是 rollers `1-2-1`、`1-2-4`，faders `3-1`、`3-2`，可能这些模块下有第二连接器。keys 与 faders 同时已知的 7 个连接器中角度相同。`gen_slots.py` 添加标记 `derived` 的推导位置，允许超出 4×6，同时保留官方条目。推导 keys `1-1-1` 为 col 2、row 0、90°，超边一格；keys `4-4` 为 col 0、row -2、90°。主人 2026-10-19 12:59–13:00 实机核对 keys `1-1-1`、`1-2-4`（derived），rollers `1-1-4`（官方但此前未核实），窗口与桌面一致，无需 Edit layout 修正，表中均标 `verified`。

**Output report 与第二 handle（2026-10-19，Windows）**：应用 reader 持一个 handle 时，用独立 HID handle 给底座发 64-byte LED 颜色只需 2.7 ms；共享 handle 要等待 reader 的 20 ms slice，达 34.8 ms。control pipe 的 `send_output_report`（SET_REPORT）被底座拒绝并卡 5 s。

20:38 构建开始，旋钮和推杆用 index `FF` 一次为整个模块着色（`02 2D <group> FF r g b 0`）；当时尚未目视核对（20:17–20:27 每 LED 一条 report 时旋钮闪动；2026-10-11 的 `FF` 已验证可设置效果）。推杆操作中两次 USB 掉线，一次发生在 LED 约 50 次/秒变化时，不能确定高频是否成因。第二次 20:09，关闭 music 时仍每 20 ms 发送 rainbow，故两次均伴高频 LED。在 10 色/秒（2026-10-19 21:06–22:58，部分时间有音乐）时保持连接。目前旋钮和推杆的 rainbow 用 index `FF` 整模块同色，`GET /api/leds` 为 10 色/秒。当晚主人说“Te podsiweltnei dobrze dziala”（这些灯光工作正常），未逐模块检查。推测而非证实：推杆固件约能处理 25 LED reports/s，不能处理 50；HubDeck 保持低于 30。

## 热拔出（2026-10-09）

取下模块导致 HID `read error`。`prototype/masterhub/hub.py` 关闭 handle，每秒扫描，模块返回时执行 `initialize()` 和 `on_connect` 重绘。测得按键拔出后 5 s 恢复。

底座接触松动会导致按压时离开 USB 约 0.5 s，Windows 播放拔出音，即使未运行任何主机软件也如此：2026-10-15 按键模块一分钟按压掉线 5 次，两侧都发生，HubDeck 已退出；取下重装后恢复。`prototype/tools/usbwatch.py` 每 0.1 s 只枚举不打开设备，打印每次 GONE/BACK。

## 按键与 dial 固件卡死（2026-10-09 确认原因）

**在 hardware mode 读取按键或 dial 的任何 feature report，都会让模块卡死直到断电复位。** 此后 feature read 返回空，USB product/serial 字符串出现乱码，含最后一次 feature response 字节，例如把 `02.00.01.00` 当 UTF-16。写命令无报错但无效，切 software mode 无法修复；只有取下重装（或重启电脑）有效。

2026-10-09 约 19:40 测试：断电复位后按键模块正常响应（`state_check.py`）；hardware mode 只执行一次 `get_feature_report(0x38)` 就卡死，未操作的 dial 仍正常。此前 dial 在 hardware mode 读取 `0x4A`、当天首次 probe 也发生同样问题。

不取下模块的恢复测试（2026-10-09 约 19:55，`prototype/tools/recover_test.py`，Windows 10）：

| 方法 | 结果 |
|---|---|
| 关闭重开 HID handle + 切 software mode | 无效 |
| 底座 hub 的 `IOCTL_USB_HUB_CYCLE_PORT`，非管理员 | 拒绝，error 31 |
| 管理员执行 `pnputil /restart-device "USB\VID_2516&PID_01FE\<serial>"` | 恢复 |
| 取下模块再装回 | 恢复 |

macOS（2026-10-13）：另一个应用刚交回模块时，从 software mode on 到首次 read 等 200 ms 并非总足够，可能卡死；改为 600 ms，读取前再发一次 software-mode command，十二次重启未卡死。

macOS 恢复待核实，候选为 IOKit 的 `USBDeviceReEnumerate`。

实现影响：

- `mh-device` 在 software mode 外拒绝读按键和 dial，返回 `Error::HardwareMode`。
- 用 device path 标识模块，不靠 USB string；切入 software mode 后从 `0x3A` / `0x4A` report 读取序列号。
- 切软件模式后仍无响应，hub 发 `Event::Unresponsive`。应用提供 Restart module（Windows UAC 执行 `pnputil /restart-device`），备用方法为重新装回。
- M0（底座、推杆、旋钮、滚轮）始终可读。

## 官方应用（MasterHUB 1.0.0.113）

- `portNumber` 来自 Node `usb` 库的 `portNumbers`，截去底座前缀，不带分隔符连接（`143`）。CSS 为 `Baseboard.vue` 中 `.<widget>.pos<path>`；widget 名为 `control-keypad`、`roller`、`knob3`、`knobx1`、`control-sliders5`。本项目 `prototype/tools/gen_slots.py` 转成 `app/src/slots.generated.json`。
- 逐键绘制 72×72、JPEG quality 60，不使用整面板。导出 `.mhz` profile；捆绑只有 Default，resources 还有 Photoshop。根据底座 input report 的 `data[0] == 1` 判 horizontal，并提供手动切换。
- 退出、休眠、设置变化时调用 `Set_Sw_Mode_CM_M4315(false)` 和 `Set_Sw_Mode_CM_M131E(false)`；本项目驱动也应如此。
- `Set_Sw_Mode(true)` 后等待 `200 * i` ms 才读 firmware。
- 独立 `MHDaemon` 每秒经 CPUID SDK（kernel driver）读 CPU/GPU sensors。作者推测与 MSI Mystic Light/Afterburner 冲突，可能导致 2026-10-09 冻结；因硬复位丢日志，没有证据。
- SDK 模块：M0（底座、推杆、旋钮、滚轮）、M131E、M4315、M3700、M3704、M4300、M4600、M5000。
