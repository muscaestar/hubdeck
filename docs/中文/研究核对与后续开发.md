## 代码阅读产生的待验证事项

以下是有明确代码依据的后续调查，不是已复现 bug 或本轮修复承诺：

- Windows 第二 writer 与 release 使用不同锁，检查应用停止 worker、归还设备之间是否始终满足不再输出的顺序。
- 插件包下载有体积上限，解压循环没有看到总展开量/条目数配额；新增配额与失败时替换回滚测试值得优先做。
- 助手 `assistant_permit` 对非 deny 字符串作 allow；应在扩展调用面前明确枚举校验。
- `guard` 对 nested steps/modes 的拒绝检查有深度上限；应确认可构造层级与执行层限制一致。
- 前端 previewCache 没有容量淘汰；长时间编辑大量图片/外观是否增长，需用可重复场景测量。
- `gen_house_style.py` 的嵌套 f-string 在本机 Python 3.11 静态解析报错；另行确认需要的 Python 版本。


另用临时失效链接做了负例验证：checker 正确报告目标不存在并以状态 1 退出，临时文件随后移除。没有把“脚本能启动”当成校验器有效的全部证据。

## 我们自己的开发顺序

1. **建立本机基线。** 独立记录这台 MasterHUB 的模块、固件、USB 路径、OS，先确认稳定接管/归还、重连、休眠和长时运行，再评估驱动可靠性。
2. **先做配置层用途。** 从 sim_panel、game_bar、shortcuts 与 vJoy binding 开始，逐个记录游戏实际绑定和实物验收。先不以 catalog 的丰富程度代替可靠性。
3. **再接赛车数据。** 用独立应用实现状态约定或插件，把游戏数据转换为清晰状态；先用 API/虚拟模块预览，再考虑专用 Rust integration 与 panel render。
4. **收紧工程边界。** 补负坐标持久化、插件解压配额、关闭时输出顺序等必要测试；将本机 UI 脚本中的作者路径/账号/数据假设参数化。
5. **决定发行策略。** 需要自己的安装版时再统一应用标识、上游同步、workflow 条件、signing/update/gallery/catalog/support URLs；文档本地化本身不改发行信任关系。

每一阶段分别记录代码检查、虚拟场景和实物观察，最后交主人验收。这样可以保留原项目的逆向成果，又知道哪些能力在这台机器上已经有证据。
